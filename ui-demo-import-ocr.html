§4 “未选文件点导入”到底发生了什么（代码事实） 对应你的两个疑问
环节事实结论
前端提交 static/components/import.js 的 handleUpload() 无文件前置校验，点击“开始导入”会无条件 fetch('/import/upload', FormData) —— 确实发出了一次导入提交请求。 是
后端拦截 app/routes/import_routes.py：未选文件时 multipart 无有效 file 字段 → FastAPI 必填参数校验返回 422；部分浏览器带空文件名 part → 命中 if not file.filename: 守卫返回 400 “❌ 缺少文件名”。两者都在业务逻辑入口被拦：不创建任务、不保存文件、不启动后台任务。测试 tests/test_import.py::test_upload_no_file_authenticated 断言 status_code in (400, 422)。 已拦截
是否触发 OCR 没有。OCR 调用链只在后台任务 _process_import() 内、且 ext == ".pdf" 且 force_ocr or is_scanned() 时才执行 create_ocr_client() → ocr_pdf_to_md()（即真正的 PaddleOCR 请求）。未选文件/缺文件名在到达后台任务之前即终止，零 OCR 请求。 否
提示文案来源 “导入失败：不支持的文件格式”由 _process_import 的扩展名白名单分支（f"不支持的文件格式: {ext}"）＋ 模板前缀“导入失败:”拼出——触发前提是文件名存在且扩展名不是 .md/.pdf（如 .docx/.png）。严格“未选文件”命中的是 400 “缺少文件名”或 422，文案不同。按代码事实，纯未选文件不会出现你看到的这句提示——你遇到的场景更可能是选了不支持格式的文件，或界面残留状态；两种情况的共同点是：请求发出但被拦截、均未触发 OCR。 文案误导
建议：上述“禁用蒙版”从入口消除误点；如同时想让“格式不支持”的提示更准确，可把错误文案改为“无法导入：仅支持 .md / .pdf 格式（当前为 .xxx）”，并补一条前端扩展名预校验（提示后不再发请求）。这两点是否纳入实施，等你定。
