# OCR 审查页改版：原文件对照 + 版面块就地编辑 — 设计

- 日期：2026-10-04
- 状态：待评审
- 关联：`docs/superpowers/specs/2026-10-02-import-task-persistence-design.md`（前置，已完成）

---

## 1. 背景与目标

用户在导入流程的原设想中提了两条（编号沿用其原始清单的第 3、4 项）：

> 3. `upload` 文件夹里是有原文件的，审查时**对照原文件的准确度是最高的**，所以是否应该改成左侧栏为原文件查看，右侧栏为 OCR 解析后的预览栏，编辑和预览操作都在预览栏完成。
> 4. OCR 审查时，对**表格内图片的修改十分不方便**，能否参考 paddle 网页导入审核，在预览栏支持表格编辑（插入行列、删除行列、合并行列）。

用户随后提供了 6 张 Paddle 网页端的实际截图作为交互参照，并明确裁定：

- **Markdown 源码不需要露出**，预览与编辑合一，改动**直接落在渲染后的排版结果上**；
- 左右两栏**操作体验要统一**（点任一侧，另一侧滚到并高亮对应块）。

**目标**：把审查页从「左 Markdown 源码 textarea + 右只读预览」改造成「**左原文件可视对照 + 右版面块所见即所得编辑**」，并把「确认并继续导入」的产物（`md_text`）保持为**与现状完全相同的格式**，从而**下游零改动**。

## 2. 范围

### 2.1 做

| # | 能力 |
|---|---|
| S1 | 左栏：原文件（PDF）逐页查看 + 缩放（4 档）+ 放大后拖动 + **版面块高亮框** |
| S2 | 右栏：按**版面块**列表现渲染，块类型标签，块角标**条文号** |
| S3 | 文本类块：就地富文本编辑（B / I / 删除线）+ 取消 / 保存 |
| S4 | 表格块：**插入/删除行列、合并/拆分单元格**，单元格内容可编辑（含**删除单元格内嵌图片**） |
| S5 | 图片块：**替换 / 删除 / 裁剪**（剪切落在**新文件**，不覆盖原图） |
| S6 | 公式块：LaTeX 输入 + **KaTeX 实时预览**；正文公式**就地展开**，表格内公式走**弹窗** |
| S7 | **双向联动**：点右栏块 → 左栏滚到并高亮；点左栏框 → 右栏滚到并高亮 |
| S8 | 搜索/替换：改造为**跨块搜索**，块内 DOM 高亮，点结果滚到该块 |
| S9 | 提交：按拼装规则**重新生成 `md_text`**，走既有 raw body 通道，**后端零改动** |

### 2.2 不做（明确排除，含理由）

| 不做 | 理由 |
|---|---|
| 块级增删 / 合并 / 拆分（新增块、删除整块） | 用户未提；OCR 错误的修正点在块**内部**与表格**结构**，不在块之间。Paddle 亦无此能力；YAGNI |
| 表内「插入/删除**单元格**」 | **用户明确改为「合并/拆分单元格」** |
| 左右栏之间的**连线** | 成本高（两个独立滚动容器持续同步）、视觉负收益（一条条文常对应多个块，多对多会糊）；Paddle 本身也没做，它用的就是双向高亮 |
| 字面 `\n` 的**批量清洗** | 会影响 `parse_markdown` 的切分（真实换行会新建行），属独立议题，见 §16 |
| 无 `layout.json` 的老任务的块编辑 | 见 §13 降级 |

## 3. 已核实的事实（实测，非推断）

### 3.1 数据侧

| 事实 | 证据 |
|---|---|
| 原文件在 `data/uploads/{task_id}{ext}` | `import_routes.py:681` |
| OCR 产物在 `data/outputs/{task_id}/{task_id}.md` + `imgs/` | `config.py:19`、实测目录 |
| `md_text` 中的表格**本就是内联 HTML** | 真实产物 `<table>` 7~262 处（`8376e02c` = 262） |
| **合并单元格本就大量存在** | `1516a11e` 实测 `colspan` 56 处、`rowspan` 111 处 |
| `parse_markdown` **不解析表格**，仅按行切编号 | `md_parser.py:788` docstring |
| `plain_text` 用 `HTMLParser` 剥标签，**天然兼容 colspan/rowspan** | `text_clean.py:24` 的 `_CELL_TAG` 只认 `</?t[dh]…>` |

> ⇒ **结论**：「合并单元格」不是要发明新格式，而是要**编辑一个本来就存在的格式**。表格编辑后序列化回 HTML，`md_text` 格式不变 ⇒ `parse_markdown` 与 `plain_text` **两端零改动**。

### 3.2 OCR 响应结构（单页真实调用实测，2026-10-04）

```
JSONL 行数 = 1（一行 = 一个文档）
record.result.layoutParsingResults[]        ← 一页一个元素
  [i].prunedResult
        width / height                      ← 页尺寸，用于坐标归一化
        dataInfo.pages[]                    ← 另有每页尺寸
        parsing_res_list[]                  ← ★ 逐块结果
        layout_det_res.boxes[]              ← 版面检测框
  [i].markdown  = { text, images }          ← 仅此两键，无块级信息
```

`parsing_res_list` 单块结构：

```json
{"block_label": "paragraph_title",
 "block_content": "目次",
 "block_bbox": [534, 201, 660, 241],
 "block_id": 0, "block_order": 1,
 "global_block_id": 0, "global_group_id": 0,
 "block_polygon_points": [[534,201],[660,201],[660,241],[534,241]]}
```

`layout_det_res.boxes` 单框结构：

```json
{"cls_id": 17, "label": "paragraph_title", "score": 0.677,
 "coordinate": [534, 201, 660, 241], "order": 1, "polygon_points": [...]}
```

### 3.3 ★ 最关键：`md_text` ↔ 块 的对应是**显式可复现**的

`markdown.text` 是 `parsing_res_list` 的**拼装产物**。实测对照：

| `parsing_res_list` | `markdown.text` |
|---|---|
| `[0] paragraph_title` / `"目次"` | `## 目次` ← **`## ` 前缀由 `paragraph_title` 生成** |
| `[1] content` / `"前言.....4  \n1 总则.....6  …"` | `前言.....4    \n1 总则.....6    …` |
| `[2] number` / `"第5页"` | **不出现** ← 在 `markdown_ignore_labels` 中被排除 |

**拼装规则**：按 `block_order` 拼「非忽略块」的 `block_content`，`paragraph_title` 加 `## ` 前缀。

⚠️ **本探针只覆盖了 1 页、3 个块，因此只**实证**了 `paragraph_title → "## "` 这一条前缀映射。**其余 label 的前缀（`doc_title` 是 `# ` 还是 `## `？`formula` 是 `$$` 还是原样？`table` 是否为原样？）**均未实测**，属实现第一步必须先钉死的项（见 §10.3 与 R7）。**不得据本节推断完整映射表。**

⚠️ **但不逐字节相等**：`block_content` 是 `.....4␣␣`（2 空格），`markdown.text` 是 `.....4␣␣␣␣`（4 空格）。⇒ 见 §10 的归一化判据与往返对拍。

> 这一条把此前唯一的红色风险项（「md ↔ block 是否显式对应」）**归零**：右栏照 `parsing_res_list` 逐块渲染，编辑后改 `block_content`，再按同一规则重新拼装即可，**不需要碰 parser，也不需要猜对应关系**。

### 3.4 渲染侧（现成可复用）

`static/components/md-render.js` 的 `renderInto/renderHtml` 已具备：

- `marked.parse(raw, {gfm:true, breaks:true})` → `DOMPurify.sanitize` → `katexize`
- **字面 `\n` → `<br>`**（`:77`），覆盖全部渲染路径
- `\(…\)` → `$…$` 兼容（`:80`）
- 图片相对路径 `imgs/` 改写为 `baseUrl + 'imgs/'`
- KaTeX `delimiters` 支持 `$…$` / `$$…$$` / `\(…\)` / `\[…\]`，`throwOnError:false`
- 孤立上标 `fixOrphanSup`、Alpine 单波浪号 `protectTildes/restoreTildes`

> ⇒ 右栏渲染**直接复用**，公式预览与表格渲染白得。

## 4. 总体架构与数据流

```
导入上传
   └─ OCR（PaddleOCR-VL）
        ├─ outputs/{task_id}/{task_id}.md      ← 现状：仅此
        └─ outputs/{task_id}/layout.json       ← 新增：parsing_res_list 精简版
                    │
审查页 /import/review/{task_id}
   ├─ 左栏  ← GET /import/review/{task_id}/page/{n}.png?scale=<float>   （新增，PyMuPDF 渲染）
   │         ← layout.json 的 bbox（百分比定位 overlay）
   └─ 右栏  ← layout.json 的 parsing_res_list（逐块渲染，复用 md-render.js）
             ← parse_markdown(md_text)（只读，用于块角条文号）
             ← 用户编辑（前端块状态）
                    │
「确认并继续导入」
   └─ 拼装(块状态) → md_text → POST /import/review/{id}/confirm（raw body，**后端零改动**）
        └─ Phase 2：parse_markdown → 分类 → 索引（**不变**）
```

**核心不变式**：对外契约仍是 `md_text`（Markdown + 内联 HTML 混排），格式不变；新增的 `layout.json` 只服务于审查页。

## 5. 数据与存储

### 5.1 `layout.json` 结构

```json
{
  "version": 1,
  "pages": [{"index": 1, "width": 1190, "height": 1684}, ...],
  "blocks": [
    {"label": "paragraph_title", "content": "目次",
     "page": 1, "bbox": [534, 201, 660, 241],
     "order": 1, "global_block_id": 0}
  ]
}
```

- **页码**：`layoutParsingResults` 的下标 + 1（一页一元素，§3.2 已证）
- **只保留**渲染与联动所需字段

### 5.2 ⚠️ 安全硬约束：**剔除签名 URL**

OCR 响应的 `outputImages.layout_det_res` / `inputImage` / `preprocessedImages` 均为**带凭据的签名 URL**（形如 `?authorization=bce-auth-v1%2F…`）。

⇒ **落盘 `layout.json` 时一律剔除**，否则等于把凭据写入磁盘、备份与分发包。此条与「分发计划脱敏名单」同源。

### 5.3 写入时机与失败处理

- `_download_markdown` 的调用点旁并行落 `layout.json`
- **落盘失败不得中断导入**（记 WARN，审查页届时降级，见 §13）

## 6. 左栏：原文件查看器

### 6.1 页图渲染

- 新端点 `GET /import/review/{task_id}/page/{n}.png?scale=<float>`
  - 后端 PyMuPDF（`fitz`，已在用）渲染，`scale ∈ [0.25, 3.0]`
  - `n` 与 `task_id` 严格校验（`task_id` 为 8 位 hex；`n` 为整数且在页数范围内）
- **端点接受任意浮点 `scale`**；UI 上的 4 档只是预设按钮
  - 理由：「适应宽度」是**算出来的实际倍数**，不是固定档

### 6.2 缩放（4 档）与拖动

| 档位 | 说明 |
|---|---|
| **适应宽度** | 默认；由容器宽 ÷ 页宽算出倍数 |
| 100% / 150% / 200% | 固定档 |

- 换档 ⇒ 按需拉取该 `scale` 的页图；**LRU 缓存**（当前页及邻近档）
- **放大后拖动**：容器 `overflow:auto`；**在无版面块区域**按下并拖动 ⇒ 改 `scrollLeft/scrollTop`（按用户要求：块上不触发拖动）
- 第三个按钮为「**重置**」—— 点击后缩放恢复「适应宽度」（**不是刷新**）

### 6.3 高亮框

- overlay 层按 `bbox / (page_w, page_h)` 的**百分比**定位
- ⇒ **缩放时框自动跟随，无需重算**（这是选百分比而非像素定位的原因）
- 框上带**块类型标签**（同 §7.2 的中文映射）

## 8. 块编辑器

### 8.1 通用交互（照搬 Paddle 范式）

```
悬停/聚焦块 → 蓝框 + 类型标签 + 右侧浮出「复制 / 纠正」
点「纠正」  → 该块就地可编辑 + 工具条 + 「取消 / 保存」
```

**保存语义**：「保存」只把改动**记进前端块状态**；真正的落库发生在「确认并继续导入」时**一次性序列化** → 与现有 raw body 通道**完全兼容，后端零改动**。

### 8.2 文本类块

- 工具条：`B` / `I` / `S`（删除线）
- 落点：对应 `block_content` 的富文本 → 序列化为 Markdown（见 §10）

**序列化映射（写死，避免二义）**：

| 富文本 | Markdown |
|---|---|
| 粗体 | `**…**` |
| 斜体 | `*…*` |
| 删除线 | `~~…~~` —— **必须成对输出** |

> ⚠️ 删除线**必须成对**：2026-10-02 刚修过「单个 `~` 被 marked 当删除线」的缺陷（`md-render.js` 的 `protectTildes`）。编辑器若输出单个 `~` 会**重新引入**该问题。

### 8.3 表格块

工具条：`B` / `I` / `S` / 表格 / 合并 / 公式 / 插入行 / 删除行 / 插入列 / 删除列

| 操作 | 语义 |
|---|---|
| 插入/删除行列 | 常规 |
| **合并单元格** | 设置 `colspan/rowspan`；**前端留一份快照**，**会话内可无损撤销** |
| **拆分单元格** | 按 `colspan/rowspan` 拆出**空白**格，恢复行列布局 |

⚠️ **拆分恢复不了内容**（用户已接受）：
- HTML 的 `colspan/rowspan` **只表达"占几格"，不保存被吞格的内容**
- 且 **OCR 产物里本就大量存在合并**（§3.1），那些被吞的格**在 OCR 那一刻就没产出内容**

⇒ 拆分后新格为空，用户自行填写；**用户自己在同一次会话内合并的**可无损撤回；**提交后不可还原**。

> **该功能的主要用途（用户说明）**：纠正「部分行列被当成图片插入一个合并的单元格」的 OCR 失效。

⇒ 因此表格编辑还需支持**删除单元格内嵌图片**（否则拆开合并格后，那张误插的图仍留在某个格里，修正不完整）。

### 8.4 图片块

| 操作 | 说明 |
|---|---|
| **替换** | 三个入口、一个落点（见下） |
| **删除** | **仅解除文档引用**（不删文件）—— 保留会话内撤回能力 |
| **裁剪** | 前端 canvas 裁切 → **另存为新文件** |

> **「删除」为什么不删文件**：编辑期的删除必须可撤回（尤其是「表格里被误当成图片的行列」这种要反复试的场景）。故**文件物理清理不在这里做**，而是放在「**确认导入之后**」—— 此时审查会话已结束，撤回需求自然到期。详见 §19。

**替换的三个入口**（用户原提两种，实测二者是同一个 `paste` 处理器；补一个更可靠的）：

| 入口 | 覆盖场景 | 可靠性 |
|---|---|---|
| **拖拽文件到块上**（drag & drop） | 替代"复制文件再粘贴" | 高 |
| **粘贴**（`paste` 事件读 `clipboardData.items`） | 截图、复制的位图 | 中 |
| **点击 → 选文件** | 兜底 | 最高 |

三者汇到同一落点：拿到 `Blob` → `POST /import/review/{task_id}/image` → 换 `img.src`。

**落盘策略（用户已定）**：
- 新图、裁剪图**一律新增文件名**，存进 `outputs/{task_id}/imgs/`，**不覆盖原图**（不可逆操作最少）

### 8.5 公式块

| 场景 | 形态 |
|---|---|
| **正文公式** | **就地展开**：`LaTeX` 标题 + 输入框 + 「公式预览」+ 取消/保存 |
| **表格内公式** | **弹窗**（格太小）同款内容 |

- 预览用 KaTeX（现成）
- **保存前校验**：KaTeX 渲染失败即为非法 LaTeX ⇒ 阻止保存并提示
- **定界符**：按原公式是行内还是块级，分别输出 `$…$` / `$$…$$`（不引入 `\(…\)`，避免额外替换路径）

| 操作 | 结果 |

## 10. 提交链路与拼装保真

### 10.1 拼装规则（单一来源）

**拼装 = 按 `block_order` 拼「非 `markdown_ignore_labels` 块」的 `block_content`；`paragraph_title` 加 `## ` 前缀。**

- 规则**只写一份**，前后端共用（建议后端提供拼装函数，前端通过一个轻端点或内联同一份规则）
- 这与 §3.3 实测一致

### 10.2 ⚠️ 已知不逐字节相等 ⇒ 必须定归一化判据

| | `block_content` | `markdown.text` |
|---|---|---|
| 同一行行尾 | `.....4␣␣`（2 空格） | `.....4␣␣␣␣`（4 空格） |

⇒ **归一化判据（建议）**：去行尾空白后逐行相等。

### 10.3 往返对拍（**必须写成测试**）

实现第一步先做「**未编辑即往返**」对拍：

```
拼装(原 layout.json 的 blocks) ≡ 原 md_text   （按 §10.2 归一化）
```

对**真实产物**（如 `411d4975`、`1516a11e`、`8376e02c`）逐份验证。**对不上就先修规则，再谈编辑功能**——否则整个改版的正确性没有地基。

### 10.4 字面 `\n` 的清洗（**纳入本次**）

`block_content` 里存在**字面 `\n`**（反斜杠 + n 两个字符），是 Paddle 的已知输出缺陷。

- **显示层**：`md-render.js:77` 已用 `.replace(/\\n/g, '<br>')` 修复 —— **这是既有解法，显示本来就没问题**
- **本次改为**：在**序列化写回时**把字面 `\n` 直接写成 **`<br>` 标签**（把渲染期的补救**前移**成存储期一次性修好）

**为什么安全**：

| 关注点 | 影响 |
|---|---|
| `parse_markdown` 切分 | **零变化** —— `<br>` 在同一逻辑行内，**不新增行**（**真实换行**才会新增行、才可能改变切分） |
| 渲染结果 | **零变化** —— 渲染时本来就把 `\n` 转 `<br>`，只是提前做了 |
| 幂等 | ✅ 渲染层再转一次是 no-op |
| 派生文本 `plain_text` | **会变**：`strip_html` 把 `<br>` 当块级标签转换行；而字面 `\n` 目前是**原样两字符**留在派生文本里 |
| 索引 | 新导入的条文**本来就是新建索引** ⇒ **无需重建**，且顺带治掉一类索引污染 |

⇒ **只对新导入生效**（审查提交时），存量不动。

**存量的清洗**（已有的规范）会改派生文本 ⇒ **必须连带重建索引** ⇒ 属独立议题（见 R6）。

> ⚠️ 关键区别：**用 `<br>` 而不是真实换行**。真实换行会新增行、可能改变条文切分 —— 这正是此前判断「不做」的原因；改用 `<br>` 后该理由不成立。

## 11. 块 ↔ 条文 对齐

### 11.1 算法

- 两侧均为**有序列表**（块有 `block_order`；条文有文档顺序）
- **贪心对齐**：把块的归一化文本往当前条文的 `content` 里凑，凑满即换下一条
- 比对前**归一化**：去 `## ` 前缀、压空白、跳过 `markdown_ignore_labels` 的块
- **对不齐就不标，不猜**（宁缺勿错）

### 11.2 无归属清单（明确不标）

| 块 | 原因 |
|---|---|
| 目次块 | 被 `parse_markdown` 的 `discard_section` **整段丢弃** |
| `number`（页号）块 | 在 `markdown_ignore_labels` 中 |
| 首个候选行之前的前导块 | 变成**孤儿隐藏块**（`is_non_clause=True`） |
| 全是次分组标签的空壳节点 | `_is_subgroup_label_only_body` 打标 |

### 11.3 价值

条文号是**唯一能提示"你这次编辑会改变条文切分"的信号** —— 恰好针对审查页最想防的失效（编号被改坏 ⇒ 静默丢条）。

## 12. 搜索/替换改造（用户已定：本次一起做）

现工具栏绑在 textarea 的 `mdContent` + 源码偏移上；块编辑后**没有"源码"**，必须改造：

| 能力 | 新实现 |
|---|---|
| 匹配计数 | 跨所有块的 `block_content` 统计 |
| 高亮 | **复用 `highlightInPreview` 的 DOM 层高亮**（走文本节点，不重渲染） |
| 上一个/下一个 | 滚动到命中块并高亮 |
| 全部替换 | 跨块替换（**保持函数式替换值**，防 `$&` 展开 —— 既有修复） |

> 既有教训须保留：`String.split` 无捕获组会静默错位 ⇒ 高亮仍用 **`exec` 逐段切分**；替换值用 `() => this.replaceText`。

## 13. 失效与降级

| 情形 | 行为 |
|---|---|
| `layout.json` 缺失（老任务 / 落盘失败） | 审查页**降级为现有纯预览**（无左栏画框、无块编辑），不报错、不阻塞 |
| 块无条文归属 | 不显示条文号（§11.2） |

| 图片上传失败 | 保留原图，提示错误，不改动块状态 |
| LaTeX 非法 | 阻止保存并提示（§8.5） |

## 18. 实施分期（**必须分期，不得一次做完**）

本设计含 9 项能力 + 一次页面重写，规模远超单个实施计划。**强制按下列分期推进，每期独立可验收**：

| 期 | 内容 | 出口判据 |
|---|---|---|
| **P0 地基** | `layout.json` 落盘（含脱敏）· label→前缀映射实测 · **拼装规则 + 往返对拍** | **对拍在真实产物上通过**。不通过则**后续全部不得开工** |
| **P1 只读对照** | 左栏页图 + 4 档缩放 + 拖动 + 高亮框；右栏块列表 + 类型标签 + **条文号对齐**；**双向联动** | 两侧点选可互相定位；老任务正常降级 |
| **P2 初次可编辑** | 文本块就地编辑 + 通用「取消/保存」+ **提交链路（序列化 → raw body）** | 编辑后导入结果与手改 md 等价；往返对拍仍通过 |
| **P3 表格** | 插删行列 · 合并/拆分 · 单元格内嵌图片删除 | 「行列被当成图片塞进合并格」这一失效可被完整修好 |
| **P4 图片 / 公式 / 搜索** | 图片三入口 + 删除 + 裁剪；公式就地与弹窗；搜索/替换跨块改造 | — |

> **P0 是硬门禁**：§10.3 的往返对拍若在 P0 未通过，**不得进入 P1**。理由是拼装规则一旦有偏差，P2 之后所有编辑都会以「静默改写 `md_text`」的形式污染导入结果 —— 而这恰是本次改版最不能承受的失效。

## 19. 与「存储治理」的衔接（本设计**不含**其实现）

审查页的「删除图片」只解除引用（§8.4），**文件回收不在本设计内**。经核实，图片残留实际落在**两个不同目录**，需要**两种不同处置**：

| # | 残留 | 位置 | 核实到的事实 |
|---|---|---|---|
| A | **整份任务残留** | `outputs/{task_id}/`（.md + imgs/） | **导入成功后无人清理**。实测 `data/outputs/` 有 **47** 个目录，而 `uploads/` 只有 **26** 个 PDF ⇒ 约 21 个是陈旧任务目录 |
| B | **长期目录里的未引用图** | `outputs/{code}/imgs/` | `_copy_ocr_images` 用 `shutil.copytree` **全量复制**（`import_routes.py:838`），**未引用的图也一并进了长期目录** |

**处置建议（两个方案都要，但对象不同）**：

- **对 A**：不必做「未引用检查」—— **整份任务目录在导入成功后就可以删**（图片已按 B 复制到长期目录）。
  - 边界：**`code` 为空时 `output_dir` 就是 `outputs/{task_id}/`**（`_copy_ocr_images` 的 `ocr_dir == out_dir` 分支）⇒ 此时不能删。该保护**已经存在**于 `_cleanup_task_artifacts` 的「被 specifications 引用则不删」守卫中，直接复用即可。
  - 现状之所以保留：`sweep_progress_store` 对 `done` 的处置是「只删台账行、磁盘留着」，理由是「可能仍被 specifications 引用」—— 但该理由对 **`code` 非空**的任务不成立。
- **对 B**：**方案二（维护页健康检查）** 才合适 —— 长期目录判「未引用」需扫描各条文的 `content`，**删错会 404**，必须由用户确认后执行。本仓已有维护页（`maintenance_routes.py`，三 Tab：健康检查 / 导出备份 / 日志管理）作为落点。

**结论**：用户的两个方案**不相悖，也不冲突，是两层的**；但**都不属于本次审查页设计** —— 属**独立的存储治理议题**，建议单独立项，避免再次撑大本 spec。

**衔接点（必须写死）**：审查页只负责「解除引用」；物理回收由存储治理在「**导入成功之后**」这个时点处理 —— 此时审查会话已结束，撤回需求自然到期。
