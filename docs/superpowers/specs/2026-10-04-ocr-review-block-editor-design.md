# OCR 审查页改版：原文件对照 + 版面块就地编辑 — 设计

- 日期：2026-10-04
- 状态：待评审
- 关联：`docs/superpowers/specs/2026-10-02-import-task-persistence-design.md`（前置，已完成）

---

## 1. 背景与目标

用户在导入流程的原设想中提了两条（编号沿用其原始清单的第 3、4 项）：

> **3.** `upload` 文件夹里是有原文件的，审查时**对照原文件的准确度是最高的**，所以是否应该改成左侧栏为原文件查看，右侧栏为 OCR 解析后的预览栏，编辑和预览操作都在预览栏完成。
> **4.** OCR 审查时，对**表格内图片的修改十分不方便**，能否参考 paddle 网页导入审核，在预览栏支持表格编辑（插入行列、删除行列、合并行列）。

用户随后提供了 6 张 Paddle 网页端的实际截图作为交互参照，并明确裁定：

- **Markdown 源码不需要露出**，预览与编辑合一，改动**直接落在渲染后的排版结果上**；
- 左右两栏**操作体验要统一**（点任一侧，另一侧滚到并高亮对应块）。

**目标**：把审查页从「左 Markdown 源码 textarea + 右只读预览」改造成「**左原文件可视对照 + 右版面块所见即所得编辑**」，并把「确认并继续导入」的产物（`md_text`）保持为**与现状完全相同的格式**，从而**下游零改动**。

## 2. 范围

### 2.1 做

| # | 能力 |
| --- | --- |
| S1 | 左栏：原文件（PDF）逐页查看 + 缩放（4 档）+ 放大后拖动 + **版面块高亮框** |
| S2 | 右栏：按**版面块**列表现渲染，块类型标签，块角标**条文号** |
| S3 | 文本类块：**行级编辑器** —— 行结构显式化（行 ↔ `md` 行一一对应），行内富文本（B / I / 删除线）+ 取消 / 保存 |
| S4 | 表格块：**插入/删除行列、合并/拆分单元格**，单元格内容可编辑（含**删除单元格内嵌图片**） |
| S5 | 图片块：**替换 / 删除 / 裁剪**（剪切落在**新文件**，不覆盖原图） |
| S6 | 公式块：LaTeX 输入 + **KaTeX 实时预览**；正文公式**就地展开**，表格内公式走**弹窗** |
| S7 | **双向联动**：点右栏块 → 左栏滚到并高亮；点左栏框 → 右栏滚到并高亮 |
| S8 | 搜索/替换：改造为**跨块搜索**，块内 DOM 高亮，点结果滚到该块 |
| S9 | 提交：按拼装规则**重新生成 `md_text`**，走既有 raw body 通道，**后端零改动** |
| S10 | **切分预览**：实时显示「当前 `md` 会被切成哪些条」，作为补写内容后验收切分的手段（§11.4） |
| S11 | **对齐（左 / 中 / 右）**：正文、图表标题、公式、表格、图片**五类块的编辑工具条都提供**（§8.6） |

### 2.2 不做（明确排除，含理由）

| 不做 | 理由 |
| --- | --- |
| 块级增删 / 合并 / 拆分（新增块、删除整块） | 用户未提；OCR 错误的修正点在块**内部**与表格**结构**，不在块之间。Paddle 亦无此能力；YAGNI |
| 表内「插入/删除**单元格**」 | **用户明确改为「合并/拆分单元格」** |
| 左右栏之间的**连线** | 成本高（两个独立滚动容器持续同步）、视觉负收益（一条条文常对应多个块，多对多会糊）；Paddle 本身也没做，它用的就是双向高亮 |
| 字面 `\n` 的**批量清洗** | 会影响 `parse_markdown` 的切分（真实换行会新建行），属独立议题，见 §16 |
| 无 `layout.json` 的老任务的块编辑 | 见 §13 降级 |
| **「段落等级 H1–H6」**（Paddle 工具条的 `Tt`） | **不做**，理由见下 |

> **为什么不做 `Tt`（用户提问后实测确认）**：
>
> 1. `parse_markdown` 的层级**只看编号点数**（`_level_from_clause_no`，注释即写明「与 Markdown 的 `#` 数量无关」）⇒ **`###` 与 `######` 对解析输出毫无区别**。「6 个选项、1 种效果」的控件本身即设计缺陷。
> 2. 它唯一真实的效果是让该行因 `#` 前缀而**无条件判标题型** ⇒ 改变 `title` / `content` 归属，并**覆盖 R14 兄弟多数表决**（一处强制可能连带动同层其他条）。
> 3. `#` 前缀行按 `re.match(r"^(#{1,6})\s+(.+)$")` 直接成**候选行** ⇒ 给非编号行加它会**凭空开出条文** —— 正是「徒增报错概率」。
> 4. **要改层级，唯一的尺子是改编号本身**（`3.0.5` → `3.0.5.1`），`Tt` 做不到。

> **⚠️ 别误读为上表禁止一切插入** —— 正向对应物如下：
>
> - **不做的是「块级」增删**（新增块 / 删除整块）：新块在原 PDF 上**没有 bbox** ⇒ 左栏无从高亮、块列表与 `layout.json` 失配。
> - **做的是「行级」编辑**：OCR 丢失的内容**在相邻块内补写**即可 —— 丢失位置在阅读顺序上**必然落在某个块的边界**，顺序天然正确。
> - 承载者：§8.2 的**行级编辑器**；验收者：§11.4 的**切分预览**。

## 3. 已核实的事实（实测，非推断）

### 3.1 数据侧

| 事实 | 证据 |
| --- | --- |
| 原文件在 `data/uploads/{task_id}{ext}` | `import_routes.py:681` |
| OCR 产物在 `data/outputs/{task_id}/{task_id}.md` + `imgs/` | `config.py:19`、实测目录 |
| `md_text` 中的表格**本就是内联 HTML** | 真实产物 `<table>` 7~262 处（`8376e02c` = 262） |
| **合并单元格本就大量存在** | `1516a11e` 实测 `colspan` 56 处、`rowspan` 111 处 |
| `parse_markdown` **不解析表格**，仅按行切编号 | `md_parser.py:788` docstring |
| `plain_text` 用 `HTMLParser` 剥标签，**天然兼容 colspan/rowspan** | `text_clean.py:24` 的 `_CELL_TAG` 只认 `</?t[dh]…>` |

> ⇒ **结论**：「合并单元格」不是要发明新格式，而是要**编辑一个本来就存在的格式**。表格编辑后序列化回 HTML，`md_text` 格式不变 ⇒ `parse_markdown` 与 `plain_text` **两端零改动**。

### 3.2 OCR 响应结构（单页真实调用实测，2026-10-04）

```text
JSONL 行数 = 1（一行 = 一个文档）
record.result.layoutParsingResults[]        ← 一页一个元素
  [i].prunedResult
        width / height                      ← 页尺寸，用于坐标归一化
        dataInfo.pages[]                    ← 另有每页尺寸
        parsing_res_list[]                  ← ★ 逐块结果
        layout_det_res.boxes[]              ← 版面检测框
  [i].markdown  = { text, images }          ← 仅此两键，无块级信息
```

`parsing_res_list` 单块结构：

```json
{"block_label": "paragraph_title",
 "block_content": "目次",
 "block_bbox": [534, 201, 660, 241],
 "block_id": 0, "block_order": 1,
 "global_block_id": 0, "global_group_id": 0,
 "block_polygon_points": [[534,201],[660,201],[660,241],[534,241]]}
```

`layout_det_res.boxes` 单框结构：

```json
{"cls_id": 17, "label": "paragraph_title", "score": 0.677,
 "coordinate": [534, 201, 660, 241], "order": 1, "polygon_points": [...]}
```

### 3.3 ★ 最关键：`md_text` ↔ 块 的对应是**显式可复现**的

`markdown.text` 是 `parsing_res_list` 的**拼装产物**。实测对照：

| `parsing_res_list` | `markdown.text` |
| --- | --- |
| `[0] paragraph_title` / `"目次"` | `## 目次` ← **`## ` 前缀由 `paragraph_title` 生成** |
| `[1] content` / `"前言.....4  \n1 总则.....6  …"` | `前言.....4    \n1 总则.....6    …` |
| `[2] number` / `"第5页"` | **不出现** ← 在 `markdown_ignore_labels` 中被排除 |

**拼装规则**：按 `block_order` 拼「非忽略块」的 `block_content`，`paragraph_title` 加 `## ` 前缀。

⚠️ **本探针只覆盖了 1 页、3 个块，因此只**实证**了 `paragraph_title → "## "` 这一条前缀映射。**其余 label 的前缀（`doc_title` 是 `# ` 还是 `## `？`formula` 是 `$$` 还是原样？`table` 是否为原样？）**均未实测**，属实现第一步必须先钉死的项（见 §10.3 与 R7）。**不得据本节推断完整映射表。**

⚠️ **但不逐字节相等**：`block_content` 是 `.....4␣␣`（2 空格），`markdown.text` 是 `.....4␣␣␣␣`（4 空格）。⇒ 见 §10 的归一化判据与往返对拍。

> 这一条把此前唯一的红色风险项（「md ↔ block 是否显式对应」）**归零**：右栏照 `parsing_res_list` 逐块渲染，编辑后改 `block_content`，再按同一规则重新拼装即可，**不需要碰 parser，也不需要猜对应关系**。

### 3.4 渲染侧（现成可复用）

`static/components/md-render.js` 的 `renderInto/renderHtml` 已具备：

- `marked.parse(raw, {gfm:true, breaks:true})` → `DOMPurify.sanitize` → `katexize`
- **字面 `\n` → `<br>`**（`:77`），覆盖全部渲染路径
- `\(…\)` → `$…$` 兼容（`:80`）
- 图片相对路径 `imgs/` 改写为 `baseUrl + 'imgs/'`
- KaTeX `delimiters` 支持 `$…$` / `$$…$$` / `\(…\)` / `\[…\]`，`throwOnError:false`
- 孤立上标 `fixOrphanSup`、Alpine 单波浪号 `protectTildes/restoreTildes`

> ⇒ 右栏渲染**直接复用**，公式预览与表格渲染白得。

## 4. 总体架构与数据流

```text
导入上传
   └─ OCR（PaddleOCR-VL）
        ├─ outputs/{task_id}/{task_id}.md      ← 现状：仅此
        └─ outputs/{task_id}/layout.json       ← 新增：parsing_res_list 精简版
                    │
审查页 /import/review/{task_id}
   ├─ 左栏  ← GET /import/review/{task_id}/page/{n}.png?scale=<float>   （新增，PyMuPDF 渲染）
   │         ← layout.json 的 bbox（百分比定位 overlay）
   └─ 右栏  ← layout.json 的 parsing_res_list（逐块渲染，复用 md-render.js）
             ← parse_markdown(md_text)（只读，用于块角条文号）
             ← 用户编辑（前端块状态）
                    │
「确认并继续导入」
   └─ 拼装(块状态) → md_text → POST /import/review/{id}/confirm（raw body，**后端零改动**）
        └─ Phase 2：parse_markdown → 分类 → 索引（**不变**）
```

**核心不变式**：对外契约仍是 `md_text`（Markdown + 内联 HTML 混排），格式不变；新增的 `layout.json` 只服务于审查页。

## 5. 数据与存储

### 5.1 `layout.json` 结构

```json
{
  "version": 1,
  "pages": [{"index": 1, "width": 1190, "height": 1684}, ...],
  "blocks": [
    {"label": "paragraph_title", "content": "目次",
     "page": 1, "bbox": [534, 201, 660, 241],
     "order": 1, "global_block_id": 0}
  ]
}
```

- **页码**：`layoutParsingResults` 的下标 + 1（一页一元素，§3.2 已证）
- **只保留**渲染与联动所需字段

### 5.2 ⚠️ 安全硬约束：**剔除签名 URL**

OCR 响应的 `outputImages.layout_det_res` / `inputImage` / `preprocessedImages` 均为**带凭据的签名 URL**（形如 `?authorization=bce-auth-v1%2F…`）。

⇒ **落盘 `layout.json` 时一律剔除**，否则等于把凭据写入磁盘、备份与分发包。此条与「分发计划脱敏名单」同源。

### 5.3 写入时机与失败处理

- `_download_markdown` 的调用点旁并行落 `layout.json`
- **落盘失败不得中断导入**（记 WARN，审查页届时降级，见 §13）

## 6. 左栏：原文件查看器

### 6.1 页图渲染

- 新端点 `GET /import/review/{task_id}/page/{n}.png?scale=<float>`
  - 后端 PyMuPDF（`fitz`，已在用）渲染，`scale ∈ [0.25, 3.0]`
  - `n` 与 `task_id` 严格校验（`task_id` 为 8 位 hex；`n` 为整数且在页数范围内）
- **端点接受任意浮点 `scale`**；UI 上的 4 档只是预设按钮
  - 理由：「适应宽度」是**算出来的实际倍数**，不是固定档

### 6.2 缩放（4 档）与拖动

| 档位 | 说明 |
| --- | --- |
| **适应宽度** | 默认；由容器宽 ÷ 页宽算出倍数 |
| 100% / 150% / 200% | 固定档 |

- 换档 ⇒ 按需拉取该 `scale` 的页图；**LRU 缓存**（当前页及邻近档）
- **放大后拖动**：容器 `overflow:auto`；**在无版面块区域**按下并拖动 ⇒ 改 `scrollLeft/scrollTop`（按用户要求：块上不触发拖动）
- 第三个按钮为「**重置**」—— 点击后缩放恢复「适应宽度」（**不是刷新**）

### 6.3 高亮框

- overlay 层按 `bbox / (page_w, page_h)` 的**百分比**定位
- ⇒ **缩放时框自动跟随，无需重算**（这是选百分比而非像素定位的原因）
- 框上带**块类型标签**（同 §7.2 的中文映射）

**✅ 与 PDF 文本层无关 —— 扫描件同样可用**：

高亮坐标**不来自 PDF 的文本层**，而来自 **PaddleOCR-VL 的版面检测**（跑在**渲染后的页图**上）：

```text
Paddle：PDF → 渲染成页图 → 在图像上跑版面检测 → bbox
我们  ：PDF → 渲染成页图（PyMuPDF）            → 按 bbox 画框
        两者都在「图像坐标系」，与文本层无关
```

⇒ **无文本层的扫描件不受任何影响**；配合百分比定位，任意渲染尺寸都能对齐。

> ⚠️ **但有一个坑**：Paddle 的 bbox 是相对**它自己渲染 / 预处理后的图**。若开启
> `useDocOrientationClassify`（方向分类）或 `useDocUnwarping`（去畸变），坐标对应的是
> **预处理后**的图，而我们左栏渲染的是**原图** ⇒ **框会错位**。
>
> - 本仓 `DEFAULT_PARAMS` 两者均为 `False` ✅，默认不错位；
> - **但可被 settings（`ocr.paddle-vl.params`）覆盖** ⇒ **设计约束：一旦开启这两个参数，左栏必须改用 `preprocessedImages` 而非自渲染页图**（否则直接禁止开启）。见 R9。
>
> 另注：**用户手打补写的内容永远不会有框**（OCR 未识别 ⇒ 无 bbox）。这是必然，不是缺陷。

## 8. 块编辑器

### 8.1 通用交互（照搬 Paddle 范式）

```text
悬停/聚焦块 → 蓝框 + 类型标签 + 右侧浮出「复制 / 纠正」
点「纠正」  → 该块就地可编辑 + 工具条 + 「取消 / 保存」
```

**保存语义**：「保存」只把改动**记进前端块状态**；真正的落库发生在「确认并继续导入」时**一次性序列化** → 与现有 raw body 通道**完全兼容，后端零改动**。

### 8.2 文本类块：**行级编辑器**

⚠️ **不是"一坨富文本"** —— 编辑器必须**显式持有「行」**，因为**行结构就是 `parse_markdown` 的切分依据**。

| 层 | 表示 | 序列化为 |
| --- | --- | --- |
| **行**（行之间） | 可独立插入 / 删除的编辑行 | **真实换行 `\n`** |
| **行内** | 富文本片段（B / I / S） | 见下方映射表 |
| **行内的字面 `\n`**（OCR 垃圾） | 两个普通字符（反斜杠 + n） | **`<br>`** —— 行**内**，不新增行（§10.4） |

**为什么必须分层**：**真实换行**与**字面 `\n`** 渲染后**都是 `<br>`，在 DOM 里无法区分**。若把整块当富文本，保存时就分不清哪些 `<br>` 该还原成 `\n`（**影响切分**）、哪些该保持不换行。**按行建模即可天然区分。**

- **行 ≡ 将来的 `md` 行** ⇒ 编号行独立成行 ⇒ `parse_markdown` 正常切
  （单个 `\n` 就够，**不需要空行** —— 判据按行扫描，空行不参与切分）
- **行的插入 / 删除** 是「补 OCR 丢失内容」的核心能力（§2.2）
- 工具条：`B` / `I` / `S`（删除线）/ **对齐**（§8.6）

**序列化映射（写死，避免二义）**：

| 富文本 | Markdown |
| --- | --- |
| 粗体 | `**…**` |
| 斜体 | `*…*` |
| 删除线 | `~~…~~` —— **必须成对输出** |

> ⚠️ 删除线**必须成对**：2026-10-02 刚修过「单个 `~` 被 marked 当删除线」的缺陷（`md-render.js` 的 `protectTildes`）。编辑器若输出单个 `~` 会**重新引入**该问题。

### 8.3 表格块

工具条：`B` / `I` / `S` / 表格 / 合并 / 公式 / 插入行 / 删除行 / 插入列 / 删除列 / **对齐（单元格内文字，§8.6）**

> **表格整体始终居中** —— 固定行为，不提供按钮（§8.6）。

| 操作 | 语义 |
| --- | --- |
| 插入/删除行列 | 常规 |
| **合并单元格** | 设置 `colspan/rowspan`；**前端留一份快照**，**会话内可无损撤销** |
| **拆分单元格** | 按 `colspan/rowspan` 拆出**空白**格，恢复行列布局 |

⚠️ **拆分恢复不了内容**（用户已接受）：
- HTML 的 `colspan/rowspan` **只表达"占几格"，不保存被吞格的内容**
- 且 **OCR 产物里本就大量存在合并**（§3.1），那些被吞的格**在 OCR 那一刻就没产出内容**

⇒ 拆分后新格为空，用户自行填写；**用户自己在同一次会话内合并的**可无损撤回；**提交后不可还原**。

> **该功能的主要用途（用户说明）**：纠正「部分行列被当成图片插入一个合并的单元格」的 OCR 失效。

⇒ 因此表格编辑还需支持**删除单元格内嵌图片**（否则拆开合并格后，那张误插的图仍留在某个格里，修正不完整）。

### 8.4 图片块

| 操作 | 说明 |
| --- | --- |
| **替换** | 三个入口、一个落点（见下） |
| **删除** | **仅解除文档引用**（不删文件）—— 保留会话内撤回能力 |
| **裁剪** | 前端 canvas 裁切 → **另存为新文件** |
| **对齐** | 左 / 中 / 右（§8.6）—— 图片居中在原文中很常见，同样属于"OCR 后丢失"的信息 |

> **「删除」为什么不删文件**：编辑期的删除必须可撤回（尤其是「表格里被误当成图片的行列」这种要反复试的场景）。故**文件物理清理不在这里做**，而是放在「**确认导入之后**」—— 此时审查会话已结束，撤回需求自然到期。详见 §19。

**替换的三个入口**（用户原提两种，实测二者是同一个 `paste` 处理器；补一个更可靠的）：

| 入口 | 覆盖场景 | 可靠性 |
| --- | --- | --- |
| **拖拽文件到块上**（drag & drop） | 替代"复制文件再粘贴" | 高 |
| **粘贴**（`paste` 事件读 `clipboardData.items`） | 截图、复制的位图 | 中 |
| **点击 → 选文件** | 兜底 | 最高 |

三者汇到同一落点：拿到 `Blob` → `POST /import/review/{task_id}/image` → 换 `img.src`。

**落盘策略（用户已定）**：
- 新图、裁剪图**一律新增文件名**，存进 `outputs/{task_id}/imgs/`，**不覆盖原图**（不可逆操作最少）

### 8.4.1 「从原文件拖框取图」—— 第四个入口（**P4，2026-10-06 用户裁定新增**）

**动机（实测，不是设想）**：OCR 对**表格单元格里的图形**不产出任何东西。实测某 122 页文档的
「表1」：表头是「编号｜名称｜**图例**｜含义」，而 48 个 `<td>` 里**图例格全空**、md 里那张表
**0 个 `<img>`**；该表所在的两页**一个 `image` 块都没有**；而**从 PDF 裁出同一区域看，图例列满满都是图**。
把 OCR 的 `maxPixels` 顶到官方范围上限（2,822,400 → 3,211,264）重跑整份文档，
结果**逐项相同**（块数 1054 vs 1054、空 `<td>` 仍 11、`<img>` 仍 0）
⇒ **这是管线的结构性行为，调参数救不回来**：表格区域整体交给表格结构识别，格内非文字图形
既不产出内容、也不作为独立 image 块下发。

于是只剩"人工把图补回来"。而**「截图 → 粘贴」两条都不划算**：截图清晰度受当前缩放档位限制
（丢分辨率），且粘出来的位图还得另做落盘与引用。故新增这个入口 —— **从原页直接取**。

| 步骤 | 说明 |
| --- | --- |
| 框选 | 在**左栏原文件**上拖出矩形 |
| 调节 | 矩形**可先调节**（拖动整体 / 拉伸边角），**右键单击确认**后才真正取图 |
| 取图 | 应用按该矩形（换算到 PDF 点）调用**已有的裁切端点** `GET /import/review/{tid}/crop/{page}.png` ⇒ 干净 PNG |
| 落盘 | 存进 `outputs/{task_id}/imgs/`，**新增文件名、不覆盖**（同 §8.4 的落盘策略） |
| 插入 | 插入**当前正在编辑的单元格**（表格格 / 图片块），引用写成 `imgs/…` 相对路径 |

**验收标准（用户原文）**：
1. 框选后可先调节范围，右键单击确认后再插入；
2. 左栏拖框的图片，能正确插入到当前编辑的单元格。

**依赖**：裁切端点已在 P3 交付（`app/routes/import_routes.py` 的 `review_block_crop`，含参数校验与夹取）；
P4 需补的是**左栏选框交互** + **落盘** + **单元格插入**三件事。

> **为什么不另做「原图对照」**（曾在 2026-10-06 讨论过）：对照图只能是**整表 bbox** 的裁切 ——
> **单元格没有各自的 bbox**（这正是上面那个失效的起因）⇒ 无法从对照图里单独抠出某一行的图例格。
> 它只省"看"（校对时行对齐），不解决"取"。**故不做，把力气放在本入口。**

### 8.5 公式块

| 场景 | 形态 |
| --- | --- |
| **正文公式** | **就地展开**：`LaTeX` 标题 + 输入框 + 「公式预览」+ 取消/保存 |
| **表格内公式** | **弹窗**（格太小）同款内容 |

- 预览用 KaTeX（现成）
- **保存前校验**：KaTeX 渲染失败即为非法 LaTeX ⇒ 阻止保存并提示
- **定界符**：按原公式是行内还是块级，分别输出 `$…$` / `$$…$$`（不引入 `\(…\)`，避免额外替换路径）
- **对齐**：左 / 中 / 右（§8.6）—— 控制的是**公式的容器**：display 公式由 KaTeX 天然居中，对齐用于整块在页面上的位置

#### 实现决定（P4 已交付，2026-10-07）

**① 表格内公式的入口（用户裁定 D1 = 方案 A）**：表格工具条加**「公式」按钮** → **弹窗**
（LaTeX 输入 + KaTeX 实时预览）→ **插入 / 替换选中格里的公式**；**一个入口同时覆盖新增与修改**
（用户不必先分辨格内有没有公式）。命中已有公式则**原地替换 `[start,end)` 并保留原定界符类型**；
未命中则**在光标处插入**（默认行内 `$…$`）。

**② 合法性校验的入口**：用 `window.katex.renderToString(tex, {throwOnError:true, displayMode})` +
try/catch。**不得**用页面现成的 `window.mdRender.katexize(root)` —— 它作用在 **DOM 容器**、且
`throwOnError:false` ⇒ 非法公式**静默保留原文、不抛也不返回布尔**，判不了合法性。
**实测可行性**：真实夹具 **21 个块级 + 177 个行内**公式在严格模式下**失败 0 例** ⇒ 不会误伤 OCR 自产公式。

**③ 公式块不得走行编辑器**：`md-inline.js` 的 `domToMd` 只认 `b/strong`、`i/em`、`s/strike/del`、`br`，
**不认 `span`** ⇒ KaTeX 渲染出的 `<span class="katex">` 若落进行编辑器，其内文本节点会被**展平**
拼回 md ⇒ **等于毁掉公式**（且是保存后才可见的静默损坏）。⇒ 公式块走**独立分支 + 独立编辑器宿主**
（与图片块同模式）。

**④ 对齐用同行 span 包裹**（`mdInline.wrap`，**不新增行**）；**实测**：包裹后 KaTeX **仍渲染**
（`f17_7` 实测 `.katex ≥ 1`），且有变异证明该断言不是假网。

### 8.6 通用属性：对齐（左 / 中 / 右）

**五类块的编辑工具条都提供**：正文、图表标题、公式、表格、图片。

**动机**：图表标题、图片在原文中常为**居中**，而 OCR 产物落到 `md_text` 后**对齐信息丢失**（实测：裸图注渲染为 `text-align: start`）⇒ **详情页永久左对齐**。`content` 是唯一存储、**导入即固化**、事后无法补 ⇒ 必须在审查页修。

**档位只做 3 档（用户已定）**：

- ✅ **左 / 中 / 右**

**明确不做另外两档**：

| 档 | 为何不做 |
| --- | --- |
| **分散对齐** | `text-align: justify-all` **Chrome 不支持**（仅 Firefox）⇒ 落地不了 |
| **两端对齐** | 中文是等宽方块字，正文 `justify` 与左对齐**几乎无视觉差别**，而真实场景是图表标题 ⇒ YAGNI |

#### ⚠️ 实现约束（**有实测支撑，不是假想**）

Markdown 段落**没有对齐语法** ⇒ 必须以 HTML 包裹表达。实测四种写法对 `parse_markdown` 的影响：

| 写法 | 切分结果 |
| --- | --- |
| ① 基线（无标签） | **2 条** ✅ |
| ② 标签与内容**同行** | **0 条** ❌❌ **全篇归零** |
| ③ 标签**独占行**（div 开 / 内容 / 闭） | 3 条 —— **多出一条伪条文**（开头的 `<div>` 行成孤儿块） |
| ④ 对齐只作用于**非编号行**、标签独占行 | **2 条** ✅ |

**② 不是"少几条"，是一条都切不出来**：所有行以 `<` 开头 ⇒ 编号判据全不命中 ⇒ **静默导入 0 条条文**。

⇒ **两条硬约束**：

1. **标签必须独占行** —— 绝不与内容同行
2. **对齐只加在非编号行上** —— 编号行的行首必须保持编号（层级与切分都依赖它）

**渲染链已实测可行**：`DOMPurify` **保留** `style` 与 `align`（`computed text-align` 确实随之变化）⇒ 不会被净化剥掉。

#### 表格：整体居中（固定行为）+ 单元格文字对齐（工具条）

| 项 | 做法 |
| --- | --- |
| **表格整体居中** | **固定行为，不是按钮** —— 无论怎么编辑单元格，表格本身**始终居中**（用户已定） |
| **单元格内文字对齐** | 工具条**只做这一级**（左 / 中 / 右），作用于**选中的单元格** |

**⚠️ 这两项都不需要外层 div 包裹 —— 用「元素自身属性」即可**（实测）：

| 写法 | 实测结果 |
| --- | --- |
| `<table align="center">` | ✅ 属性保留，`margin-left/right` 计算为 auto ⇒ 整体居中生效 |
| `<table style="margin-left:auto;margin-right:auto">` | ✅ 同样生效 |
| `<td align="center">` | ✅ 保留，`computed text-align` = `-webkit-center` |
| `<td style="text-align:center">` | ✅ 保留，`computed text-align` = `center` |

⇒ **不新增行、不动行首** ⇒ **对 `parse_markdown` 的切分风险为零** —— 优于上文给文本行用的 div 包裹方案。

> 若某张表是 **Markdown 管道表**（本仓 OCR 产物是 HTML 表，但用户上传的 `.md` 可能有），单元格对齐改用**分隔行的 `:` 语法** —— 该语法同样**不改变行数**，安全。

**⇒ 因此上文那两条硬约束（标签独占行 / 只作用于非编号行）约束的是「文本行的对齐」；表格这两项不受其限制。**

**适用范围（用户已定：方案 b）**：**所有**表格（**含未编辑的**）在提交时**统一**加居中 —— 即「**居中是本项目的表格规范**」。

⚠️ 这会**改变未被用户碰过的表格的 `md_text`** ⇒ 与 §10.3 的往返对拍**冲突**。处置见 §10.3 的「与规范化步骤的次序」。

## 10. 提交链路与拼装保真

### 10.1 拼装规则（单一来源）

**拼装 = 按 `block_order` 拼「非 `markdown_ignore_labels` 块」的 `block_content`；`paragraph_title` 加 `## ` 前缀。**

- 规则**只写一份**，前后端共用（建议后端提供拼装函数，前端通过一个轻端点或内联同一份规则）
- 这与 §3.3 实测一致

### 10.2 ⚠️ 已知不逐字节相等 ⇒ 必须定归一化判据

同一行行尾的空白数量不同：

- `block_content`：`.....4␣␣`（**2 空格**）
- `markdown.text`：`.....4␣␣␣␣`（**4 空格**）

⇒ **归一化判据（建议）**：去行尾空白后逐行相等。

### 10.3 往返对拍（**必须写成测试**）

实现第一步先做「**未编辑即往返**」对拍：

```text
拼装(原 layout.json 的 blocks) ≡ 原 md_text   （按 §10.2 归一化）
```

对**真实产物**（如 `411d4975`、`1516a11e`、`8376e02c`）逐份验证。**对不上就先修规则，再谈编辑功能**——否则整个改版的正确性没有地基。

#### ⚠️ 与「表格居中规范化」的次序（用户已定方案 b）

「所有表格统一居中」（§8.6）会**改变未编辑表格的 `md_text`** ⇒ 若把它混进对拍，**地基判据就模糊了**。故**强制分两步**：

| 步 | 内容 | 判据 |
| --- | --- | --- |
| **1（P0 门禁）** | 对拍**只**证明**拼装规则本身**正确 —— **不加任何规范化** | `拼装(原 blocks) ≡ 原 md_text`（§10.2 归一化） |
| **2（其后独立）** | 表格居中规范化，作为**独立一步**，**有自己的测试** | **条文数与 `clause_no` 序列不变**（`content` 多出 `align` 属性属预期） |

> **理由**：§10.3 的往返对拍是整个改版**唯一的地基**。一旦掺入「有意的规范化」，它就从"证明拼装正确"退化成"证明拼装+规范化凑巧相等"，**判据失去意义**。

### 10.4 字面 `\n` 的清洗（**纳入本次**）

`block_content` 里存在**字面 `\n`**（反斜杠 + n 两个字符），是 Paddle 的已知输出缺陷。

- **显示层**：`md-render.js:77` 已用 `.replace(/\\n/g, '<br>')` 修复 —— **这是既有解法，显示本来就没问题**
- **本次改为**：在**序列化写回时**把字面 `\n` 直接写成 **`<br>` 标签**（把渲染期的补救**前移**成存储期一次性修好）

**为什么安全**：

| 关注点 | 影响 |
| --- | --- |
| `parse_markdown` 切分 | **零变化** —— `<br>` 在同一逻辑行内，**不新增行**（**真实换行**才会新增行、才可能改变切分） |
| 渲染结果 | **零变化** —— 渲染时本来就把 `\n` 转 `<br>`，只是提前做了 |
| 幂等 | ✅ 渲染层再转一次是 no-op |
| 派生文本 `plain_text` | **会变**：`strip_html` 把 `<br>` 当块级标签转换行；而字面 `\n` 目前是**原样两字符**留在派生文本里 |
| 索引 | 新导入的条文**本来就是新建索引** ⇒ **无需重建**，且顺带治掉一类索引污染 |

⇒ **只对新导入生效**（审查提交时），存量不动。

**存量的清洗**（已有的规范）会改派生文本 ⇒ **必须连带重建索引** ⇒ 属独立议题（见 R6）。

> ⚠️ 关键区别：**用 `<br>` 而不是真实换行**。真实换行会新增行、可能改变条文切分 —— 这正是此前判断「不做」的原因；改用 `<br>` 后该理由不成立。

## 11. 块 ↔ 条文 对齐

### 11.1 算法

- 两侧均为**有序列表**（块有 `block_order`；条文有文档顺序）
- **贪心对齐**：把块的归一化文本往当前条文的 `content` 里凑，凑满即换下一条
- 比对前**归一化**：去 `## ` 前缀、压空白、跳过 `markdown_ignore_labels` 的块
- **对不齐就不标，不猜**（宁缺勿错）

### 11.2 无归属清单（明确不标）

| 块 | 原因 |
| --- | --- |
| 目次块 | 被 `parse_markdown` 的 `discard_section` **整段丢弃** |
| `number`（页号）块 | 在 `markdown_ignore_labels` 中 |
| 首个候选行之前的前导块 | 变成**孤儿隐藏块**（`is_non_clause=True`） |
| 全是次分组标签的空壳节点 | `_is_subgroup_label_only_body` 打标 |

### 11.3 定位：**验收工具，不是装饰**

条文号不只是"告诉用户这块属于哪一条"。它是**唯一能提示「你这次编辑会改变条文切分」的信号** —— 针对的正是审查页最想防的失效（编号被改坏 ⇒ 静默丢条）。

配合 §11.4 的切分预览，它从**只读装饰**升级为**编辑结果的验收手段**。

### 11.4 切分预览（**验收用**）

**动机**：用户补写 OCR 丢失的内容时，真正的顾虑不是"写不进去"，而是「**写进去了但切分不对**」——新条文没被切出来，或把相邻条吞掉。

**方案**：编辑区旁**实时显示「当前 `md` 会被切成哪些条」** —— 直接跑 `parse_markdown`（或前端按同一判据预览），列出 `clause_no` + `title` 摘要。

- 用户补完一段 ⇒ **立刻看到新条文有没有出现、有没有把相邻条吞掉**
- 若全量渲染太重（870 条 / 46 万字符），退化为**只显示受影响片段**，或**防抖 + 按需触发**
- **这是本次改版对「保证切分准确」最有价值的一项** —— 价值高于编辑器本身的可靠性

## 12. 搜索/替换改造（用户已定：本次一起做）

现工具栏绑在 textarea 的 `mdContent` + 源码偏移上；块编辑后**没有"源码"**，必须改造：

| 能力 | 新实现 |
| --- | --- |
| 匹配计数 | 跨所有块的 `block_content` 统计 |
| 高亮 | **复用 `highlightInPreview` 的 DOM 层高亮**（走文本节点，不重渲染） |
| 上一个/下一个 | 滚动到命中块并高亮 |
| 全部替换 | 跨块替换（**保持函数式替换值**，防 `$&` 展开 —— 既有修复） |

> 既有教训须保留：`String.split` 无捕获组会静默错位 ⇒ 高亮仍用 **`exec` 逐段切分**；替换值用 `() => this.replaceText`。

**三条补充事实（P4 已交付，2026-10-07）**：

**① 块页此前「零搜索」⇒ 本次实为「新建」，不是「改造」**：`ocr_review_blocks.html` 里
`grep search/replace/toolbar` **零命中** —— 旧源码审查页那套绑 textarea + **源码偏移**的模型在此页
**不成立**（块页没有 textarea）。故 §12 表里的「改造」在块页落地时是从零新建一整套搜索工具条。

**② 搜索范围 vs 替换范围（用户裁定 D2）**：搜索覆盖**所有「进 md 的块」**（判据是 **`label` 是否在该任务
真实的 `not_in_markdown` 名单里**，**与有无 `span` 无关**）；**替换**只作用于**可编辑块**；命中不可编辑块时
**禁用替换并给出可见原因**（**不得静默**）。

**③ 计数口径是字符串域（刻意取舍，不是缺陷）**：显示的数取 `countIn(contentOf(b), q)`（**字符串域**）；
而高亮走 **DOM 文本节点**（**不跨元素边界**）⇒ **高亮数可能低于计数**。追求两数相等需要维护
「源码偏移 ↔ DOM 文本节点」映射表，**收益不抵复杂度**，故**刻意**允许两者不同。

## 19. 与「存储治理」的衔接（本设计**不含**其实现）

审查页的「删除图片」只解除引用（§8.4），**文件回收不在本设计内**。经核实，图片残留实际落在**两个不同目录**，需要**两种不同处置**：

| # | 残留 | 位置 | 核实到的事实 |
| --- | --- | --- | --- |
| A | **整份任务残留** | `outputs/{task_id}/`（.md + imgs/） | **导入成功后无人清理**。实测 `data/outputs/` 有 **47** 个目录，而 `uploads/` 只有 **26** 个 PDF ⇒ 约 21 个是陈旧任务目录 |
| B | **长期目录里的未引用图** | `outputs/{code}/imgs/` | `_copy_ocr_images` 用 `shutil.copytree` **全量复制**（`import_routes.py:838`），**未引用的图也一并进了长期目录** |

**处置建议（两个方案都要，但对象不同）**：

- **对 A**：不必做「未引用检查」—— **整份任务目录在导入成功后就可以删**（图片已按 B 复制到长期目录）。
  - 边界：**`code` 为空时 `output_dir` 就是 `outputs/{task_id}/`**（`_copy_ocr_images` 的 `ocr_dir == out_dir` 分支）⇒ 此时不能删。该保护**已经存在**于 `_cleanup_task_artifacts` 的「被 specifications 引用则不删」守卫中，直接复用即可。
  - 现状之所以保留：`sweep_progress_store` 对 `done` 的处置是「只删台账行、磁盘留着」，理由是「可能仍被 specifications 引用」—— 但该理由对 **`code` 非空**的任务不成立。
- **对 B**：**方案二（维护页健康检查）** 才合适 —— 长期目录判「未引用」需扫描各条文的 `content`，**删错会 404**，必须由用户确认后执行。本仓已有维护页（`maintenance_routes.py`，三 Tab：健康检查 / 导出备份 / 日志管理）作为落点。

**结论**：用户的两个方案**不相悖，也不冲突，是两层的**；但**都不属于本次审查页设计** —— 属**独立的存储治理议题**，建议单独立项，避免再次撑大本 spec。

**衔接点（必须写死）**：审查页只负责「解除引用」；物理回收由存储治理在「**导入成功之后**」这个时点处理 —— 此时审查会话已结束，撤回需求自然到期。

## 20. `.md` 上传的审查入口（**新增范围**，与 B 组同批）

**背景（已核代码）**：`.md` 上传**目前完全没有审查环节** —— `_process_import` 的 `.md`
分支是「读文件 → `clean_ocr_text` → **直接 `_process_import_phase2`**」，从不经过
`review_needed`（`app/routes/import_routes.py:749-755`）。

**决定（用户 2026-10-04）**：**保留现有的「左 Markdown 源码 / 右预览」设计**（即磁盘上现存
的 `partials/ocr_review.html`），作为 **`.md` 上传的审查页**；OCR 审查走新建的版面块页。
**两个入口，两套范式。**

### 20.1 这不与「Markdown 源码不露出」矛盾

那条铁律是**为 OCR 用户**立的：他们的正确做法是**对照原文件**，不该去读源码。
而 **`.md` 上传的用户自己就带着 md 来** —— 露出源码天经地义、甚至必需。

| 入口 | 判据 | 左栏 | 右栏 |
| --- | --- | --- | --- |
| OCR 审查 | `.pdf` | 原文件页图 + 高亮框 | 版面块就地编辑 |
| **md 审查** | `.md` | **Markdown 源码（textarea）** | **预览** |

### 20.2 入口分派：单一判据

**按 `task["file_name"]` 的扩展名**分派。**不得**另加状态字段或 flag。

### 20.3 ⚠️ 三处必须定死，否则埋雷

| # | 坑 | 处置 |
| --- | --- | --- |
| 1 | **图片 404** —— md 里若引用 `imgs/xxx.jpg`，md 路径**不产出 `imgs/`** | 预览中隐藏外链图片，或给明确占位（实现时二选一） |
| 2 | **清洗次序** —— 现在是「读 → `clean_ocr_text` → Phase 2」 | 改为「读 → `clean_ocr_text` → **`review_needed`**」。**必须先清洗再审查**，否则用户改好的内容提交后**又会被清洗一遍** |
| 3 | **不得另造一套** | 复用现有 `ocr_review.html` 与 `POST /import/review/{id}/confirm`（raw body）⇒ **后端零改动** |

### 20.4 结构性约束：**必须与 B 组同批**

B 组要改的正是 `review_page` 路由与模板选择。**若 B 组先改完，md 入口就不存在了**
（因为现在压根没建过）。⇒ 本项列为 B 组的一期，与页面重写**同批**。

### 20.5 不做

- **md 审查页不做版面块编辑 / 表格编辑器** —— md 用户手里就是源码，改源码最直接。
- md 入口**不需要 `layout.json`**（它天然属于「无 layout」路径）。
