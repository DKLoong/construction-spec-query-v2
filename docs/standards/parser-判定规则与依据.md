**R7 / R7b 是本轮最有价值的一条**：它是「主控项目/一般项目当条文属性、不进层级路径」这个
设计决策的**法定依据**——不是我猜的，而是原文明确写了它是「次分组单元」且
「所属节的条文编号应连续」（编号连续 = 它不占据层级位置）。

**R14 是本轮另一条高价值发现**：现有 parser 用 `_looks_like_title`（**≤20 字且无句末标点**）
判断编号行是"标题型"还是"正文型"——这是个**代理指标**，所以
`3.0.1 接头设计应满足强度及变形性能的要求`（16 字、无句号）被误判成标题型而丢失。

而 §7.3.3 给了一条**有原文依据的替代判据**：
> 某一章或条中，其下一个层次上的各条，**有无标题应一致**。例如 6.2 的下一层次，
> 如果 6.2.1 给出了标题，6.2.2、6.2.3 等也需要给出标题，或者反之，该层次的条都不给出标题。

即：**同层次的兄弟条文「有无标题」必须一致** → 可以用**兄弟一致性**（多数表决）
替代单行的字数阈值。这比 `≤20 字` 稳健得多，且能直接修掉 `3.0.1` 那类误判。
（注：R14 出自 GB/T 1.1，其「条」对应 182 号的「条」；规则精神可平移。）

**R13 可用于结构校验**：既能发现"孤立编号"（同级只有一个条）这类可疑切分，
也**反向提示不要凭单行臆造层级**。

## 二、版本比对（1996 vs 2008）：**纯叠加，零冲突**

引自《工程建设标准编写规定》1996 版（建标〔1996〕626 号附件一）第三章原文：

| 规则 | 1996 版 | 2008 版 | 差异性质 |
|---|---|---|---|
| 层次 = 章/节/条/款/项 | ✓ 第二十二条 | ✓ 第三十二条 | 相同 |
| 章/节/条定义 | ✓ 第二十三条 | ✓ 第三十三条 | 相同 |
| 编号 = 阿拉伯数字 | ✓ 第二十四条（圆点加在数字的**下角**） | ✓ 第三十四条（**右下角**） | 措辞微调 |
| 章内不分节用 `0` | ✓ 第二十五条（**节的编号**用"0"） | ✓ 第三十五条（**条号中对应节的编号**用"0"） | **含义相同**，2008 更明确 |
| 款=阿拉伯数字、项=右半括号 | ✓ 第二十六条 | ✓ 第三十六条 | **相同** |
| 附录=大写正体字母从 A 连续 | ✓ 第二十七条（**拉丁**字母） | ✓ 第三十七条（**英文**字母） | 措辞微调 |
| **排除字母** | **I、O** | **I、O、X** | ★ 2008 **多排除 X** |
| **次分组单元 + 大写罗马数字** | **✗ 无** | **✓ 新增** | ★ 2008 新增 |
| **单表/单图附录（表C/图C）** | **✗ 无** | **✓ 新增** | ★ 2008 新增 |

**结论**：核心编号语法两版**完全一致**，2008 只是**新增**了三条 → **叠加关系，无「同形状异义」冲突**
→ **用并集语法（一套规则覆盖所有年代）即可，不必按年份分派规则**（用户已认可）。

### 由版本比对直接推出的一个具体规则选择

**附录排除名单只取 `I`、`O`（两版共有），保留 `X`**：

- 1996 版只排除 I、O → **老规范里理论上可能出现 `附录X`**
- 2008 版排除 I、O、X
- 若按 2008 的名单去排除 X，会**漏掉老规范里的 `附录X`**
- 解析器的原则是"宁可多认、不可误漏" → **只排除 I、O**

## 三、由 R3 推出的层级语义（本轮树设计直接用到）

R3 原文明确是「**条的编号中对应节的编号**应采用"0"表示」，因此：

- `X.0.Y` = 章 `X` 下**无节**，直接是条 `Y` → **层级链里没有「X.0」这个节节点**
- 反例（错法）：把 `3.0.1` 拆成 章3 → 节0 → 条1，会凭空造出一个叫「0」的节
- 正确：`3.0.1` 的父链 = [`3 章`]，层级深度按"去 0 后"的段数计

CJJ2/JGJ107 里大量 `X.0.Y`（如 `3.0.1`、`7.0.1`）就是这个法定写法，**不是异常**。

## 四、硬证据：语料实测（2026-09-26）

> 与规则表相互独立，用于**验证解析器行为**；改 parser 时必须回归。

### 4.1 语料构成

```
目录内 PDF 共 126 份
  ├ 像规范编号的（GB/JGJ/CJJ/JTG/JT/TB/DB/CECS…）: 59 份
  └ 非规范（公司文件/通知/作业指导书/指南）      : 67 份  ← 不会导入知识库
```

**教训**：任何"形态覆盖率"统计都必须先剔除非规范文档。本目录里
`中文顿号 20%`、`第X条式 11%` 两个形态**几乎全部来自非规范文档**。

### 4.2 形态 × 年代（仅文本层文件）

```
年代        份数  X.Y.Z  X.Y  X.0.Y  第X条  第X章/节  附录  罗马  中文顿号
1995-2007    2   2/2   2/2   2/2   0/2    0/2    2/2  1/2   0/2
2008-2019   10   7/10  7/10  5/10  0/10   3/10   6/10 2/10  0/10
≥2020        8   5/8   5/8   4/8   0/8    5/8    6/8  5/8   0/8
```

- `X.Y.Z / X.Y / X.0.Y / 附录` 在**最早的 1995-2007 规范里就已全部存在** → 编号语法跨年代稳定
- **`第X条` 在规范里 0 命中** → **不需要支持**（它只出现在非规范文档）
- **`中文顿号` 在规范里 0 命中** → **不支持**（用户已裁定），且它本非规范形态

### 4.3 切分质量（CJJ 2-2008 / JGJ 107-2016）

```
                      CJJ2      JGJ107
源结构编号(去重)        850        84
库中条文号             754        73
召回                 744/850=87%  71/84=84%
  ├ 漏掉的「内节点」     103         12     ← 章名/节名
  └ 漏掉的「真叶节点」      3          1     ← 18.8.9 / 日期碎片2008 / 英文标题 ; 3.0.1
臆造出「数字编号」         0          0     ← 数字条文号切得很准
库中「不含数字的条文号」   123         2     ← 伪条文号（主控项目54/一般项目59/英文标题…）
「主控项目/一般项目」吞走的字符  209,366 = 全规范正文 47%
```

### 4.4 向量截断（检索质量的最大洞）

```
模型 BAAI/bge-small-zh-v1.5  max_seq_length = 512
附录A 的 embed_text 实测 1,624 tokens → 只保留 512 → 丢弃 68%
永不进向量索引的正文占比：CJJ2 = 67.2%   JGJ107 = 75.9%
```
（FTS 侧不受影响——`build_search_text` 不截断；所以现象会被混合检索掩盖。）

### 4.5 目次 vs PDF 书签（同一份 CJJ2，两条独立来源）

```
目次编号 135 个 | 书签编号 133 个 | 目次 ∩ 书签 = 133  →  书签 ⊆ 目次
仅目次有: 20.3、21.3（书签漏了这两个节，且 20.3 在正文里确实存在）
```
**结论**：**目次是超集、书签是子集**。书签不可靠有三重表现：漏节（20.3）、
全是占位（GB 50202-2018 的 95 条全是 `page-41`）、层级重复（低压配电 GB50054 的
L2/L3 是同一批节名）。→ 书签**不当真值、也不当输入**，最多做交叉校验的第二来源。

## 五、由 R8/R8b 发现的具体缺口（非条文块名单）

182 号第七条给了**权威清单**，逐项对照现有代码与**库内实测**（`spec_query.db`）：

| 权威非条文块 | 代码覆盖 | 库内实测 |
|---|---|---|
| 封面 / 扉页 | ✅ `is_cover_clause`（特征词 ≥2 判定） | CJJ2 封面页已丢弃 ✓ |
| **公告** | ❌ **未覆盖** | **spec20 有 2 条伪条文**：`中华人民共和国住房和城乡建设部 公告`、`关于发布行业标准《城市桥梁工程施工与质量验收规范》的公告` |
| 前言 | ✅ `_NON_CLAUSE_EXACT_TITLES` | spec19/20 均打标 `clause_is_non=1` ✓（spec20 有 2 条「前言」重复） |
| 目次 / Contents | ✅ 直接过滤 | ✓ |
| **标准用词说明** | ⚠️ **只覆盖一种写法** | spec19 `本规程用词说明` → `clause_is_non=1` ✓；**spec20 `本规范用词说明` → 未被认定，成普通条文**（代码检查的是 `本规范用词用语说明`，多个"用语"） |
| **引用标准名录** | ❌ **未覆盖** | 标题本身被 emit 守卫丢掉，但**其列表项被误吞成两条伪条文**：`clause_no='1'`、`clause_no='10'`（内容是 `2《不锈钢棒》GB/T 1220` 这类标准清单） |
| 条文说明 | ✅（含子串匹配） | ✓ 打标保留 |

**结论**：需要补 **公告**、**引用标准名录** 两项，并**把「标准用词说明」改成按法定名称匹配**。

> **处置方式的依据分级**（注意区分）：
> - **原文只规定了"它们属于标准构成、不是章/节/条"**（第六、七条）—— 这一层有原文依据
> - 至于"**打标保留**（留档但默认不进检索池）还是**直接过滤**（不进库）"，
>   **原文没有规定，是我们的设计选择**。建议与「前言」一致取"打标保留"，
>   理由是它们含可追溯信息（公告号、被替代标准、引用标准清单），留档有用但不应参与检索。
>   **此条待你在设计中确认。**

**这条正是"按见过的写法逐个补"的教训**：代码里收的是 `本规范用词用语说明`，
而 CJJ2 写的是 `本规范用词说明` → 差两个字就漏了。182 号第三十条的**法定名称**
是「**标准用词说明**」，应以法定名称为准、再兼容变体，而不是继续按见过的写法枚举。

## 七、`section_path` 格式规范（面包屑快照）

> **为什么单列一节**：规则表（§一）只讲「怎么判定层级」，没有讲**判定结果的字符串长什么样**。
> 而这一串有**四个直接消费方**（详情页「来源：」、条文列表逐行、向量的 `embed_text`、
> FTS 的 `breadcrumb` 独立列），任何一个消费方按自己的猜想解析，就会静默错位。
> 1 年后改 parser / 写检索 / 调展示的人**都会**踩，故在此写死。

**唯一产出点**：`app/parser/md_parser.py::_build_section_path`（祖先链的拼接）。
`clauses.section_path` 存原始快照（供展示），`clauses.breadcrumb` 存同一串的 jieba 预分词
结果（供 FTS 的独立列）——两者**同源但不同形**：后者是分词后以空格连接的词元串，
**分隔符 ` > ` 本身是纯标点、被 `app/search/tokenize.py::tokenize` 过滤掉了**，
故它**不出现**在 `breadcrumb` 里（实测同一条文：`section_path` = `"5 混凝土分项工程 > 5.1 模板"`，
`breadcrumb` = `"5 混凝土 分项 工程 5.1 模板"`，串里没有 `>`）。
⇒ **不要在 FTS 的 `breadcrumb` 列里 grep 分隔符**，那是查不到的；要还原层级请读
`section_path`（展示用），要分词命中请查 `breadcrumb`（检索用）。

**逐条回答五个必问点**：

| 问题 | 答案 | 依据 |
|---|---|---|
| 分隔符是什么 | **` > `** —— 一个空格 + `>` + 一个空格（`" > ".join`） | 代码 |
| 每段是否含编号 | **含**，且**编号在前、标题在后**：`"6 混凝土分项工程"` | `f"{clause_no} {title}"` |
| `X.0.Y` 的 `0` 段是否出现 | **不出现**。`3.0.1` 的父链只有章 `3`（面包屑形如 `"3 <章标题>"`），不会凭空造出「节 `3.0`」 | **R3**，见 §三 |
| 次分组单元（主控项目/一般项目）是否出现 | **不出现**。它们是**条文属性、不占层级**，且这类标签行不是编号候选行，根本进不了祖先栈 | **R7 / R7b** |
| 无祖先时是什么 | **空串 `""`** —— 不是 `None`，也不带尾随分隔符 | `_build_section_path` docstring |

**三个同样会踩的边界**（都属格式本身，不是实现细节）：

- **只含祖先、不含自身**：祖先链取栈中 `stack[:-1]`，当前条自己**不进**串
  （`5.1.1` 的面包屑是它的上级 `"5 混凝土分项工程 > 5.1 模板"`）。
- **祖先标题可以为空 → 该段只剩编号**（`f"{clause_no} {title}".strip()` 去掉尾随空格）。
  R14 兄弟表决把某个编号行判为**正文型**时 `title=''`（该行本身仍是条文、仍入祖先栈），
  其子条文的面包屑于是出现 `"3"` 这样的**裸编号段**（`md_parser.py` 中记录过实测值 `'3'`）。
  ⇒ **解析面包屑时不要假设每段都形如「编号 空格 标题」**。
- **非条文块不进面包屑**：祖先若带 `is_non_clause`（前言 / 条文说明等）会被过滤掉——
  它们不是结构层级，进了面包屑就是把「来源」写错。

**与 `parent_clause` 的关系（两套层级表示，别只信一套）**：`clauses.parent_clause` 存的是
同一祖先信息的**行 id** 版本 —— **最近现存祖先**的 clause id，批二起**已填充**（此前恒为 NULL，
故 `app/maintenance/health_check._count_orphan_parent` 那项检查也**跟着由死代码变成活检查**：它此前
恒为 0，现在真能查出悬空引用；详细说明见 `app/database.py` 该列旁的注释）。
两种表示共用的不变量是「**父级编号是子级编号的段前缀**」（`21.4.1` → 父级编号 ∈ {`21.4`, `21`}）；
⚠ 孤立计数**只验外键存在性**，写入方填一个库里存在的 id 就恒绿（哪怕指向一条无关的更早条文），
故该不变量另有断言钉住，改动上游时不要打破它。
